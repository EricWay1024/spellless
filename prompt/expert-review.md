# Expert review of docs/ALGORITHM.md

Received 2026-09-06, in response to `docs/ALGORITHM.md`. Reproduced verbatim.

---

Here is what I found, roughly in order of how much I think each is worth. I'll start with one reframing that several of the later ideas hang off.

The score is already a noisy-channel model, just unnormalised. Read the ranking function as $\log P(w \mid q) = \log P(w) + \log P(q \mid w) + \text{const}$: the $w_f \cdot f(w)$ term is $\log P(w)$ rescaled, $-w_c \cdot \text{cost}$ is $\log P(q \mid w, k)$ for channel $k$ if each edit price is a negative log-probability, and $\text{base}[k]$ is $\log \pi_k$, the mixture weight of that channel. The $\max$ over sources is the usual Viterbi approximation to the mixture sum. So §8.2's "principled formulation" is not a replacement, it is a diagnosis: the two things a real noisy channel has that this doesn't are consistent units and normalisation. Units first. If the log-frequency range is $R$ nats, then $w_f = 34$ means $34/R$ points per nat, and $w_c = 16$ means one unit of edit cost is worth $16R/34 \approx 0.47R$ nats of frequency. For a Google Books list $R$ is around 15–18, so a single 1.00 edit is being priced at roughly $e^{-7}$ to $e^{-8}$, i.e. a unit repair to a word is believed only if the word is a few thousand times commoner than the exact alternative. That number is either right or wrong, but it is a single dial, and it is currently split across two constants that coordinate descent moves independently. Normalisation is the more interesting gap and it explains two of your hand-won rules. A generative model of abbreviation must satisfy $\sum_q P(q \mid w) = 1$, and a long word has vastly more subsequences than a short one, so an unnormalised per-skip price systematically favours long words; the tail-charging rule in §4.5 is a crude normaliser and the doubled-letter fix is another. The clean version for the cue channel is to give every character of $w$ a keep probability by class, $p_v$ for vowels, $p_c$ for clustered consonants, $p_o$ for onsets, charge $-\log p$ when the typist kept it and $-\log(1-p)$ when they skipped it, and the model normalises itself. Keeping is currently free, which is exactly why a vowel-rich input can pass as shorthand; charging kept vowels at $-\log p_v$ with $p_v$ small reproduces your $V(2\alpha - 1)$ vowel-ratio term as a consequence rather than a hack, and it is per-position rather than a global ratio. Three probabilities replace three costs plus $V_{cue}$ plus most of the tail rule.

That model has one more payoff, which is that it can be fitted with no corpus at all. The alignment DP already tells you, for any committed pair $(q, w)$, which characters were kept and which skipped; class-wise keep probabilities are then closed-form counts. So §8.7's store of (typed, committed) pairs is also the training data §8.2 says it lacks, and even one user produces enough pairs in a week to fit three numbers per person. Whether that user drops leading vowels, keeps $y$, keeps onsets, becomes learned rather than asserted, and the learning is a table of counts, hence inspectable and undoable, which satisfies 8.0.5.

On the held-out problem, there is a free fix you should take before anything else. The generated sets come from a seeded generator. Run tune.lua on seed A and report on seed B, and also do leave-one-file-out over the twelve case files. That turns §5.2 from training accuracy into something defensible for the 1,200 generated cases at zero cost, and the size of the gap between seeds is itself the most useful number you don't currently have. Separately, the cost–frequency interaction you suspect is one constant away: replace $w_c \cdot \text{cost}$ with $w_c \cdot \text{cost} \cdot (1 + \beta(1 - f(w)))$ and let coordinate descent find $\beta$. If $\beta$ comes out near zero the linear form was fine; if not, you have your answer without the probabilistic rewrite.

Context, §8.1. A word bigram over 83k words is not affordable, but a class bigram is, and it targets exactly the biggest failure class. Morphological siblings almost always differ in part of speech (regulator/regulatory, generate/generation, America/American, habit/habitat is the exception), and the previous word predicts part of speech far better than it predicts the word. Assign each dictionary entry one byte of class (a coarse tag set, 30–60 classes, from any public tagged lexicon, or Brown-style clusters) and ship a class-by-class log-probability table, which is a few kilobytes. Then add $w_{ctx} \cdot \mathrm{PMI}(c(w); c(\text{prev}))$ to the score. PMI rather than $\log P$ is the answer to your combination question: it is zero-centred, so an unknown or unreadable previous word contributes nothing, it is bounded in practice, and it is a log-ratio, so it enters at the same points-per-nat you already have. Gate it on the previous token being a dictionary word followed by exactly one space, and apply it only to candidates within some margin of the leader, so it can reorder siblings but cannot overturn an exact match. Cost is one table lookup per candidate. If you want zero external data, an even smaller hand-written version already settles most siblings: determiners and prepositions predict a noun, to predicts a verb, very and more predict an adjective or adverb. The vowel-identity class (motions/meetings, blocks/blacks) is nouns against nouns and no class model helps; only a real bigram or the personal store does, and a personal previous-word bigram is cheap to add to the §8.7 file.

One generation model, §8.3. I would not build a trie in Lua tables; at 100 or so bytes a node it blows the memory budget. But you don't need one, because the sorted alphabetical permutation is an implicit trie: the words extending a prefix form a contiguous range, and extending by one character is a binary search that narrows the range. A best-first search over states (range, DP column, cost so far) with a budget is a Levenshtein automaton without the automaton, in zero extra memory, and it subsumes exact, prefix and typo in one pass with the cost profile as a parameter. Where I think it stops is the cue channel: with vowel skips at 0.04 the search tree fans out over every vowel of every word, and the bucketed scan with the mask test is honestly the right structure for subsequence matching. The one unification I would do there is cheaper than a trie: for each first letter, precompute 26 bitsets over that bucket, one per letter, saying which words contain it. Lua 5.4 has 64-bit integers, so a 3,000-word bucket is about 50 integers per letter, 26 by 26 by 50 integers overall, tens of kilobytes. The letter-set test for a query becomes $|q|$ ANDs of 50 integers instead of a 3,000-word scan, and it also makes relaxing the first-letter requirement affordable, which §8.4 needs.

Fuzzy composition, §8.4. Two separate things are hiding in this item, and one of them is small. A slip inside shorthand needs only a substitution transition in the subsequence DP at around 1.0, plus relaxing the mask test to $\mathrm{popcount}(q_{mask} \wedge \neg w_{mask}) \le 1$. Same scan, same budget structure, and it covers stfxctn without touching segmentation. Fuzzy segmentation is the genuinely expensive one, but there is a reuse trick: aligning a dictionary word against the query with the query as the DP's row index gives you, in the final column, the cost of that word explaining every prefix $q[1..i]$ at once, so one DP per candidate word yields all its split points. A two-word lattice then needs one bounded fuzzy search from position 1 plus one from each surviving split point, and you gate the whole thing on the single-word channels returning nothing trustworthy, which by §4.9 is already a computed predicate. Most keystrokes never pay; the rare ones pay a few milliseconds.

Incremental search, §8.6. The non-monotonicity you describe is real for the budget-cut candidate set but not for a slack set. Under any of the profiles, appending one character changes a word's alignment cost by at most a bounded amount $\Delta$ (the most expensive single edit, 1.00, or a bit more with transposition), so every word inside budget for $q + c$ was inside $\text{budget} + \Delta$ for $q$, provided it was visited at all. That last clause is the only real work: widen the length window by one at generation time and keep the slack pool with its DP rows, then each keystroke extends every kept row by one and re-generates only for the newly admissible length bucket. For the cue channel it is cleaner still, since both the subsequence property and the mask test are monotone in $q$, so the pool only shrinks, apart from the growing length ceiling. This is what pays for 8.1 and 8.4 at the 8–9 character peak.

Remember the input, §8.7. The design I would use is the one every CJK IME converged on: store (typed, committed, count, last used), treat an exact match on typed as a source with a high base, but let it lead only once count is at least 2. A single selection gets a bonus that cannot overturn the leader; the second selection promotes it. That is what stops one accident becoming permanent without asking the user to press forget. Decrement when the stored candidate is shown and not chosen, cap the file by LRU. This also removes the eys/eyes pathology from the general vocabulary term, since the misspelling is now tied to the input that produced it rather than raised everywhere.

Frequency data, §8.5. wordfreq (subtitles, web, Wikipedia, news, blended) and the OpenSubtitles frequency lists are both open and both fix the mathew/mather/mathews problem directly, because names are rare in speech-like text. Blend in the log or Zipf domain, not in counts, so scale differences don't matter, and treat capitalised-in-corpus tokens as a separate class for the §8.1 table rather than demoting them, since the same tokens are exactly what a surname typist wants. On the compression of rank 100 versus rank 10,000: using Zipf units directly and letting the points-per-nat calibration above set the weight is the principled version of what you have.

Two smaller things. The typo bucket keys on the query's first or second letter, which misses a substituted first letter that is not a QWERTY neighbour; adding buckets for the neighbours of $q[1]$ is two or three more binary searches. And the transposition-abort bug is the kind that a property test catches for free: random string pairs against a plain reference DP, a few hundred per run.

Finally a note on the misses in §6: several of the sibling cases are ones where the system's answer is the better reading of the input (rgulator ends in the letters of regulator, vegtal in those of vegetable, accor is a prefix of both), so part of that 62% is the test set expressing a preference the input cannot support. Context is the only honest fix, and until then those rows are slightly overstating the residual.
